# Running Observe on Kubernetes

Chart: `packaging/helm/observe`. It deploys one Observe pod and one Nucleus pod
(both StatefulSets), mirroring `docker-compose.yml`.

Status of this chart: written against the compose file and systemd units. It has
not been installed on a cluster, and `helm lint` / `helm template` had not been
run when it was written (no Helm in the authoring environment). The
`.github/workflows/helm.yml` workflow runs lint, template and kubeconform; treat
a green run of that workflow as the first real validation.

## Single instance only

Replicas are fixed at 1 in the templates and there is no `replicaCount` value
(the schema rejects unknown keys, so `--set replicaCount=2` fails). Observe has no
clustering: the ingest WAL and queue under `OBSERVE_DATA_DIR` are owned by one
process, and Nucleus runs as a single node. A second replica, or two releases
pointed at one database, is unsupported and can corrupt WAL state or
double-process events. The HA position is in `docs/design/ha-and-clustering.md`
(that file and `docs/operations/hardening.md` come from a separate change; read
them there if they are not in your checkout).

Consequences:

- A PodDisruptionBudget is not provided. With one replica `minAvailable: 1`
  would block node drains forever and `maxUnavailable: 1` does nothing. A drain
  restarts the pod; acknowledged events are covered by the durable WAL
  (default mode) and replayed on start.
- Readiness removes the single pod from the Service while it is degraded, so
  senders get connection errors rather than the application's 503. SDKs should
  retry.
- Rolling updates restart the pod (the old one stops before the new one starts,
  since the volume is ReadWriteOnce). Expect a short ingest gap.

## Install

```sh
kubectl create namespace observe
kubectl -n observe create secret generic observe-secrets \
  --from-literal=OBSERVE_JWT_SECRET="$(openssl rand -hex 32)" \
  --from-literal=OBSERVE_SESSION_SALT="$(openssl rand -hex 32)"
helm install observe packaging/helm/observe -n observe \
  --set secrets.existingSecret=observe-secrets \
  --set observe.publicUrl=https://observe.example.com
```

The image tag defaults to the chart `appVersion` (release tags have no `v`
prefix). Nucleus is pinned to `v1.1.1` (`nucleus.image.tag`); the schema rejects
`latest`.

## Secrets

| Variable | Required | Chart behavior |
|----------|----------|----------------|
| `OBSERVE_JWT_SECRET` | yes | Rendering fails unless provided or autogenerated |
| `OBSERVE_SESSION_SALT` | yes | Same |
| `OBSERVE_SECRET_KEY` | no | Needed to configure LLM/S3 credentials; encrypts them at rest |
| `OBSERVE_ADMIN_PASSWORD` | no | Unset means the `/setup` wizard creates the admin |

Choose one:

1. `secrets.existingSecret` (preferred). Key names default to the variable names
   and are overridable under `secrets.keys`. The chart cannot check the Secret's
   contents, only that you named one. `OBSERVE_SECRET_KEY` and
   `OBSERVE_ADMIN_PASSWORD` are optional keys.
2. `secrets.jwtSecret` + `secrets.sessionSalt` as values (they land in the
   Helm release record; avoid for real deployments).
3. `secrets.autogenerate=true`: generated once and reused on upgrade through
   `lookup`, with `helm.sh/resource-policy: keep`.

Regenerate-on-restart trap (same failure `teploy.yml` documents): if the JWT
secret or salt is empty, Observe generates fresh random ones on every start,
invalidates every session and changes visitor/session IDs, and logs only a WARN.
On Kubernetes the equivalents are:

- `lookup` returns nothing under `helm template`, `helm install --dry-run`,
  Argo CD and Flux, so `autogenerate` produces new values on every render there.
  Use `existingSecret` with those tools.
- Deleting the release removes an inline-value Secret. Re-installing with
  different values logs everyone out.
- Changing a Secret does not restart the pod; run
  `kubectl rollout restart statefulset/<release>-observe`.

`OBSERVE_SECRET_KEY` loss makes stored LLM/S3 credentials unreadable. Back it up
with the same care as the data.

## Nucleus is unauthenticated: network isolation

Nucleus runs with `NUCLEUS_ALLOW_NO_AUTH=1` (as in compose and systemd). Anyone
who can open a TCP connection to it can read and write all data. The chart:

- exposes it through a `ClusterIP` Service only, and offers no Ingress,
  NodePort or LoadBalancer option for it;
- publishes only the database port (5432) on the Service; the cluster port
  (5433, required by the compose flags) is not exposed;
- renders a NetworkPolicy allowing ingress to the Nucleus pod only from the
  Observe pod of the same release, on the database port.

NetworkPolicy is enforced only if your CNI supports it (Calico, Cilium, and
similar). On a cluster without enforcement the policy is silently ignored and
any pod in the cluster can reach the database. Verify with a throwaway pod:

```sh
kubectl -n observe run np-test --rm -it --image=busybox --restart=Never -- \
  nc -zv -w 3 observe-observe-nucleus 5432   # must time out
```

Do not set `nucleus.networkPolicy.enabled=false` on a shared cluster. For
stricter setups add your own egress policy for the Observe pod and, ideally,
dedicate a namespace. With `nucleus.enabled=false` (external database) none of
this applies; securing that database is yours.

## Probes

`/healthz` runs `SELECT 1` against Nucleus and returns 503 when the database is
unreachable or ingest durability is degraded (dead flush worker, WAL failure,
memory-only WAL, failing error flush). The chart uses it for:

- startup probe (up to 180 s) and readiness probe, with 12 s timeouts to cover a
  cold Nucleus connect (~7.8 s measured, see the Dockerfile `HEALTHCHECK`).
  A 503 marks the pod NotReady.
- Not for liveness. Liveness is a TCP check on the dashboard port, so a database
  outage does not restart-loop Observe. Read the `/healthz` body to see why a
  pod is NotReady.

## Storage and backup

| PVC | Mount | Holds |
|-----|-------|-------|
| `data-<release>-observe-0` | `/var/lib/observe` | ingest WAL/queue (`queue/`), `audit.key`, local state |
| `data-<release>-nucleus-0` | `/data` | all analytics data |

Both are ReadWriteOnce (`persistence.*`). `helm uninstall` does not delete
StatefulSet PVCs; do not delete them by hand either.

Back up:

1. Both PVCs, with CSI VolumeSnapshots taken as close together as possible. The
   WAL is replayed against Nucleus at start, so (by design reading, not tested)
   a slightly older Nucleus snapshot with a newer WAL snapshot is the safer
   skew; the reverse risks losing the acknowledged tail. Crash-consistency of a Nucleus snapshot has not been
   verified here; also take Observe's application-level backup periodically.
2. `audit.key` (in the Observe PVC) and `OBSERVE_AUDIT_KEY` if you set it; losing
   the key breaks verification of the audit chain.
3. The Secret holding `OBSERVE_SECRET_KEY`, JWT secret and salt.

The pod root filesystem is read-only; `/tmp` is an `emptyDir`
(`tmpSizeLimit`, default 1Gi) where backup and restore stage temporary files.
Size it above your largest table export.

## Exposure

The dashboard Service is `ClusterIP`. To publish it, use `ingress.*` (with
`ingress.tls` and a pre-created or cert-manager TLS Secret) and set
`observe.publicUrl` and `observe.trustedProxies` to your ingress controller's pod
CIDR so client IPs are not spoofable.

To collect telemetry from outside without exposing the dashboard, enable the
split listener:

```yaml
ingest: { enabled: true, port: 3001 }
ingress:
  enabled: false            # dashboard stays internal
  ingest: { enabled: true, host: ingest.example.com, tls: { enabled: true, secretName: ingest-tls } }
```

This sets `OBSERVE_INGEST_ADDR=:3001`, adds `<release>-observe-ingest`, and its
Ingress points only at that Service. The first-run `/setup` wizard is on the
dashboard port only; with no admin password set, complete setup (via
port-forward) before exposing the dashboard.

## Security context and resources

Observe runs as uid/gid 10001 (the Dockerfile user) with a read-only root
filesystem, all capabilities dropped, no privilege escalation, `RuntimeDefault`
seccomp, and `fsGroup: 10001` so the PVC is writable. The only writable paths
are the data PVC and `/tmp`. The read-only root filesystem was derived from
reading the code (temp files and the data dir are the writes found); it has not
been run. If a feature fails with a read-only error, set
`securityContext.readOnlyRootFilesystem=false` and report the path.

The Nucleus container drops capabilities and escalation but keeps the image's
user and a writable root filesystem, because its image layout was not verified.

Resource defaults come from `BENCHMARKS.md` (91 MB idle, 124 MB after the full
benchmark, Nucleus 72 to 100 MB on a 4-core test box) with headroom for the
100000-event buffer and `--max-memory 512`: Observe requests 100m / 128Mi and is
limited to 1Gi; Nucleus requests 100m / 256Mi, limited to 768Mi. No CPU limits
are set, to avoid throttling ingest. Those benchmarks are from small hardware;
size from your own traffic (see `docs/operations/capacity.md`).

## Values reference

See `packaging/helm/observe/values.yaml` (commented) and `values.schema.json`.
Any `OBSERVE_*` setting not modeled as a value goes in `observe.env` (plain) or
